# ADR 0036 — FIPS 140-3 validated crypto module mode for jess

| | |
|---|---|
| **Status** | Proposed |
| **Phase** | 5j-2 (continues 5j-1 hardware-bound operator keys; precedes 5j-3 per-session MFA step-up) |
| **Owners** | Platform / jess maintainers |
| **Date** | 2026-06-03 |
| **Supersedes** | none |
| **Required by** | Federal customer eligibility (FedRAMP moderate baseline, SOC 2 CC6 transmission/storage controls, DoD IL2+, OMB M-22-09 cryptographic posture); ADR 0034 priority #2 |

## Problem

jess today uses Go's default crypto stack (`crypto/tls`, `crypto/ecdsa`, `crypto/ed25519` via the Vault Transit backend, `crypto/aes` for AEAD, `crypto/sha256` for the audit chain) plus a Rust IronRDP broker (ADR 0033) that uses `rustls` with the default `aws-lc-rs` backend. **No FIPS 140-3 validated cryptographic module is currently in use.**

Federal procurement requires that "cryptographic modules" — not just cryptographic *algorithms* — be validated under the NIST Cryptographic Module Validation Program (CMVP). FIPS 140-2 modules enter Historical status after **2026-09-21** (six weeks from this ADR's date), at which point FedRAMP moderate / IL2+ / DoD CC SRG packages effectively require FIPS 140-3 validated modules for new authorizations. Tier-1 PAM vendors all offer a FIPS-validated build today:

- **Teleport Enterprise** — releases 17.7.3+ and 18.0.0+ compile against `BoringCrypto` tag `fips-20220613` (CMVP cert #4735, FIPS 140-3). Earlier 17.x releases used `fips-20210429` (cert #4407, FIPS 140-2). Per ADR 0034 §"FIPS 140-3 validated crypto mode" jess is currently **N** while Teleport is **Y**.
- **AWS Verified Access / Google IAP / Cloudflare Access** — all FIPS-validated cryptographic modules (BoringCrypto for Google, AWS-LC for AWS, BoringSSL for Cloudflare).
- **CyberArk PSM, HashiCorp Boundary Enterprise** — Vault Enterprise FIPS Inside (Leidos-attested for FIPS 140-3 in Vault Enterprise 1.19.4+).

ADR 0034's Decisions §Top-5 ranks FIPS 140-3 mode as **priority #2** (after hardware-bound operator keys), labelled effort **M** (multi-week). This ADR scopes that work.

### Teleport's choice and what we learn from it

Teleport ships their FIPS build with `GOEXPERIMENT=boringcrypto` linked against a frozen BoringCrypto tag. They chose this because Go's native FIPS module was not yet CMVP-certified at their 17.x/18.x release timelines. **As of 2026-06-03, Go's native FIPS module v1.0.0 has a CMVP cert (#5247)**, so the trade-off has shifted in favour of native — no cgo, no GOEXPERIMENT label, supported on all Go-supported platforms, single binary, no boringssl runtime dependency.

## Decision

**Adopt Go 1.24+ native FIPS 140-3 mode** as the primary cryptographic posture for jess controller, jess worker, jessctl, and the Falcon-ID-adjacent services jess imports as libraries. **Fall back to `GOEXPERIMENT=boringcrypto`** if a CMVP cert revocation or an unexpected validation block surfaces during 5j-2c CI build-up.

For the Rust component (`jess-ironrdp-broker`, ADR 0033), **adopt `aws-lc-rs` with the FIPS feature flag** as the `rustls` crypto provider.

**Vault PKI** (the `jess-ca` mount that issues operator certs, the `jess-smartcard-ca` mount planned in ADR 0033 §5f-8b-3, the `jess-ssh-client-signer` mount, and the Transit backend backing per-session WORM Ed25519 signing) MUST run on Vault Enterprise FIPS Inside (or HCP Vault Plus, which carries Vault Enterprise FIPS Inside by default). Vault Enterprise 1.19.4+ is Leidos-attested for FIPS 140-3.

### Why native Go over boringcrypto

Cross-validated against ADR 0034 §Decisions priority #2:

1. **No cgo** — jess builds today are pure Go. `GOEXPERIMENT=boringcrypto` introduces cgo dependency on the BoringSSL fipsmodule.a, breaking static binaries, cross-compilation, and our existing CI (Talon CI lane runs `go build -trimpath -ldflags="-s -w"` for the controller image; cgo breaks reproducibility).
2. **CMVP cert is real** — #5247 issued; the prior 2025 risk of "pending review" is closed.
3. **Multi-arch + multi-OS** — `boringcrypto` is linux-amd64 + linux-arm64 only. jessctl ships for darwin-arm64, linux-amd64, and linux-arm64 today (`make jessctl-all`). Native FIPS works on every Go-supported platform including darwin (with the caveat that the FIPS provider on darwin still routes through Go's pure-Go implementation — see §Failure modes).
4. **Single source of truth** — Go upstream owns the cert. No third-party fork rot. The 1.26.0 successor is already in CMVP "In Process," so the upgrade path is clear.

### Why aws-lc-rs over alternatives for Rust

1. **First Rust-native FIPS-validated module.** AWS has a CMVP cert for the underlying AWS-LC module (FIPS 140-3 level 1).
2. **rustls upstream supports it.** `rustls = { features = ["aws-lc-rs"] }` is the documented config; the FIPS-bound build flips a feature flag on `aws-lc-rs` itself.
3. **No cgo from Rust.** `aws-lc-rs` ships pre-built static libraries for the supported targets; Rust toolchain links them directly.
4. **The IronRDP broker already uses `rustls`** for the operator TLS leg (`services/ironrdp-broker/crates/broker-bin/`). The migration is a feature flag flip + dependency add, not a rewrite.

## Design / implementation

### Crypto inventory (Phase 5j-2a deliverable)

jess's crypto-using surface, mapped to FIPS 140-3 approved status:

| Use site | Algorithm | FIPS 140-3 status | Where |
|---|---|---|---|
| Operator cert issuance | EC P-256 + ECDSA-SHA256 | **Approved** (FIPS 186-5 §6) | Vault PKI `jess-ca/operator-cert`; verified per-handshake on `:7101` |
| Operator cert revocation | CRL signed RSA-2048 SHA-256 | **Approved** | Vault PKI CRL |
| Worker–controller mTLS | EC P-256 + ECDSA-SHA256 + AES-256-GCM + SHA-384 (TLS 1.3) | **Approved** | `internal/spine/transport_tls.go`; yamux multiplex |
| Operator port TLS (`:7101`) | EC P-256 + ECDSA + AES-256-GCM + SHA-384 | **Approved** | `internal/admin/server.go` |
| Admin port TLS (`:7103`) | EC P-256 + ECDSA + AES-256-GCM + SHA-384 | **Approved** | `internal/admin/server.go` |
| WORM recording per-session signature | Ed25519 via Vault Transit | **Approved** (FIPS 186-5 final, 2023-02-03, includes deterministic Ed25519) | `internal/recording/signer.go` |
| Cross-session audit chain | SHA-256 | **Approved** | `internal/audit/chain.go` (Phase 5e-16) |
| Falcon-ID JWT verification | ES256 (ECDSA P-256 SHA-256) + HS256 fallback | **Approved** | `internal/oidcverify/` |
| SSH-CA cert issuance | EC P-256 + Ed25519 | **Approved** | Vault SSH `jess-ssh-client-signer` |
| Postgres broker dyn-creds | TLS 1.3 (as above) | **Approved** | `internal/dbproxy/` |
| HTTP proxy recording | TLS 1.3 + SHA-256 (Phase 5h-3) | **Approved** | `internal/httpproxy/` |
| Asciicast manifest hashing | SHA-256 | **Approved** | `internal/recording/manifest.go` |
| Risk-score evaluator | n/a (no crypto) | n/a | `internal/risk/` |
| Operator session token (Phase 5g-6 grant-tick) | HMAC-SHA-256 | **Approved** | `internal/admin/granttick.go` |

**Conclusion of inventory: every jess cryptographic primitive is FIPS 140-3 approved.** No algorithm migration is required; the work is purely *module provenance* — routing every call through a validated module instead of Go's default implementation.

**Disallowed primitives (must not be introduced):**
- `crypto/md5` (non-approved)
- `crypto/sha1` outside HMAC contexts (legacy HMAC-SHA1 in TLS 1.2 CBC mode is still allowed in 140-3 transitional mode, but we set TLS 1.3-minimum so this never matters)
- `crypto/rc4`, `crypto/des`, `crypto/des/3des` (forbidden)
- TLS 1.0 / TLS 1.1 / TLS 1.2 without P-256/P-384 ECDHE
- RSA-1024 / DSA / DH groups < 2048

**Enforcement:** custom golangci-lint analyser `jessfipsanalyser` that fails CI on any `import "crypto/md5"`, `import "crypto/sha1"`, `import "crypto/rc4"`, `import "crypto/des"` outside `_test.go` files. Lints third-party deps via `go list -m all` cross-check against a denylist. (Initial denylist sourced from BoringCrypto's `crypto/internal/boring/notboring.go`.)

### Runtime flag — `JESS_FIPS_MODE`

New env var, evaluated at controller, worker, and jessctl startup:

```go
// internal/fipsmode/fipsmode.go (new)
package fipsmode

import (
    "crypto/internal/fips140"  // import path stable as of Go 1.24
    "fmt"
    "os"
)

const EnvVar = "JESS_FIPS_MODE"

type Mode string

const (
    ModeOff      Mode = "off"      // default; pure-Go path
    ModeOn       Mode = "on"       // FIPS mode required at boot
    ModeRequire  Mode = "require"  // FIPS mode required AND non-approved algorithms panic
)

// MustEnable inspects JESS_FIPS_MODE and the runtime module status,
// returning an error (fatal at boot) if the requested mode is not active.
func MustEnable() error {
    mode := Mode(os.Getenv(EnvVar))
    switch mode {
    case "", ModeOff:
        return nil
    case ModeOn, ModeRequire:
        if !fips140.Enabled() {
            return fmt.Errorf("jess: JESS_FIPS_MODE=%s requested but FIPS 140-3 module not active (GODEBUG=fips140=on missing or Go build without FIPS support)", mode)
        }
        return nil
    default:
        return fmt.Errorf("jess: invalid JESS_FIPS_MODE=%q (want off|on|require)", mode)
    }
}
```

`MustEnable()` is called from:
- `cmd/jess-controller/main.go` (very first line of main, before any TLS listener binds)
- `cmd/jess-worker/main.go` (same)
- `cmd/jessctl/main.go` (only when `--fips` flag is passed by the operator)

On failure: **process exits with code 78 (`EX_CONFIG`)**. A controller failing to boot in FIPS mode emits an audit event `fips_mode_boot_failed` with the resolved Go FIPS module version + error string. This event MUST land in MinIO WORM bucket via the cross-session chain (not just stderr) so a misconfigured deploy is auditable.

The runtime flag pairs with the **build-time configuration**:

```
GOFIPS140=v1.0.0 go build -tags fips -trimpath \
    -ldflags="-s -w -X github.com/HexxLock/jess/internal/fipsmode.BuildMode=fips" \
    -o bin/jess-controller-fips ./cmd/jess-controller
```

`GOFIPS140=v1.0.0` pins the validated module version into the binary. `GODEBUG=fips140=on` at runtime activates it (or `=only` for the `require` mode).

### Build tag `fips` and CI lane `build:jess-fips`

A new Go build tag `fips`:
- Adds a constant `internal/fipsmode.BuildTag = "fips"` (zero on default builds, `"fips"` on FIPS builds).
- Imports `crypto/internal/fips140` via an init() that asserts module presence.
- Gates any code paths that would otherwise fall back to non-approved algorithms (e.g. an HKDF helper currently using a custom expander would switch to `crypto/hkdf` which is FIPS-routed in 1.24+).

CI matrix extension (`.gitlab-ci.yml` on the `jess` repo):

```yaml
build:jess-controller-default:
  extends: .go-build
  variables:
    BINARY: jess-controller
    GOTAGS: ""
    IMAGE_TAG: ${CI_COMMIT_SHA}

build:jess-controller-fips:
  extends: .go-build
  variables:
    BINARY: jess-controller
    GOFIPS140: "v1.0.0"
    GOTAGS: "fips"
    IMAGE_TAG: "fips-${CI_COMMIT_SHA}"
  script:
    - |
      go build -tags "$GOTAGS" -trimpath -o bin/$BINARY ./cmd/$BINARY
      # smoke-test: a Go test that asserts fips140.Enabled() under GODEBUG=fips140=on
      GODEBUG=fips140=on go test -tags fips ./internal/fipsmode/... -run TestModuleActive
```

Helm chart (`charts/jess/values.yaml`):

```yaml
image:
  tag: "fips-abc1234"      # operator picks fips-* tag to opt in
  fipsMode: "require"      # OFF | on | require
env:
  - name: JESS_FIPS_MODE
    value: "{{ .Values.image.fipsMode }}"
  - name: GODEBUG
    value: "fips140=on"
```

A nightly **acceptance test** runs both default and fips images through the same e2e suite (Phase 5 SSH brokering, Phase 5h-3 HTTP proxy, Phase 5e-16 chain verify) to catch regressions where a fips-tagged path silently drops support for an operation the default path handled.

### Vault FIPS Inside provisioning

`infrastructure-iac/datacenters/eu-west-1/vault/` already deploys Vault HA. **Image swap** from `hashicorp/vault:1.20.0` to `hashicorp/vault-enterprise-fips:1.20.0-ent.fips1403` is the smallest change. Caveats:

1. **License requirement.** Vault Enterprise Plus (HSMs) tier is required for the `fips1403` feature name — not the base Vault Enterprise tier. The license file at `vault-jess-prod/license` must include the `vault.hsm` feature. Confirm with HashiCorp account team before image swap.
2. **HCP Vault alternative.** HCP Vault Plus ($1.58/hr per cluster on 2026 pricing) carries Vault Enterprise FIPS Inside by default; no per-feature licensing complexity. Trade-off: lose self-hosted control of the audit log destination.
3. **Migration path.** Run a parallel `vault-enterprise-fips` cluster, replicate via Vault's performance replication, dual-write for 24h, flip the `vault-active` Kubernetes Service to the new pods, retire the old cluster.

**Out-of-scope of this ADR:** the actual TF MR; that lives in `iac/` and is gated on the license confirmation.

### Rust broker (`jess-ironrdp-broker`)

Phase 5j-2d adds the `aws-lc-rs` FIPS feature to the workspace `Cargo.toml`:

```toml
[workspace.dependencies]
rustls = { version = "0.23.x", features = ["aws-lc-rs"] }
aws-lc-rs = { version = "1.x", features = ["fips"] }
```

In `crates/broker-bin/src/main.rs`, the TLS server config now constructs `rustls::ServerConfig` via `rustls::crypto::aws_lc_rs::default_provider()` rather than `rustls::crypto::ring::default_provider()`. The FIPS feature flag in `aws-lc-rs` binds to AWS-LC-FIPS 3.0.x (currently CMVP-validated; ML-KEM included).

Container image: parallel `fips-<sha>` tag built via a new CI lane mirroring the Go one. The binary is statically linked against the AWS-LC-FIPS C library; Buildkit produces a single-arch (linux-amd64) image because AWS-LC-FIPS does not currently certify on arm64. **This blocks an arm64 FIPS broker until AWS-LC-FIPS certifies arm64** (tracked in §Open questions).

## Cross-cutting concerns

### CI matrix doubling

Every release tag now produces **two** images per service (default + fips). Image storage doubles; Harbor retention sweep policy at `infrastructure-iac/.../harbor/jess-project-retention.tf` MUST be updated to retain both tags symmetrically. The retention-swept-pinned-image incident on 2026-05-30 (Memory entry internal engineering notes) is the cautionary precedent — Composition pins to a fips-tagged image will hit the same trap if retention sweeps it.

### Falcon-ID coupling

Falcon-ID issues the JWTs jess verifies. If Falcon-ID is NOT also in FIPS mode, the verification chain is only as strong as the weakest link from an auditor's perspective. **Falcon-ID FIPS mode is a parallel ADR** in the `falcon-id` repo and MUST be tracked as a dependency in the 5j-2 rollout plan. Until Falcon-ID is FIPS, jess's FedRAMP package needs an SSP entry noting the upstream IdP module status.

### Talon coupling

Talon (the IAP fronting jess.hexxlock.com:7101) similarly needs FIPS posture for full federal eligibility. Talon's own ADR for FIPS is **not** scoped here; jess's posture remains independently meaningful (the broker's own TLS endpoints and audit primitives are validated) but a complete FedRAMP package needs Talon too. Cross-track in the Hexx tier-1 platform roadmap.

### MinIO audit-archive bucket

MinIO (WORM-locked bucket `audit-archive`) uses its own TLS stack. The MinIO version in production today runs the default Go stdlib crypto. For full FIPS posture of the *recording chain*, MinIO must also be on a FIPS build. MinIO Enterprise has a FIPS build; the OSS edition does not. **Decision:** flag this in the FedRAMP boundary discussion (§Open questions) — the recording's *signature* is FIPS-validated (Ed25519 via Vault Transit FIPS mode) even if MinIO's at-rest encryption is not, so the signature integrity argument holds; the at-rest layer requires a separate decision.

## Failure modes

| Failure | Detection | Mitigation |
|---|---|---|
| Go FIPS module CMVP cert revoked between build and deploy | CMVP RSS feed monitoring; alert in `monitoring/` | Block fips-tagged image deploys via Kyverno policy; rollback to `GOEXPERIMENT=boringcrypto` path (5j-2c fallback lane stays warm) |
| `JESS_FIPS_MODE=require` requested but binary built without `fips` tag | `fipsmode.MustEnable()` returns error; process exits 78 | Audit event + alert; Helm chart includes a templating-time assertion that `image.tag` starts with `fips-` when `fipsMode != off` |
| Third-party dep introduces non-FIPS algorithm in a transitive import | `jessfipsanalyser` golangci-lint rule fires on `go list -m all` denylist cross-check at build time | Block CI; pin the dep to a previous version or fork it |
| Vault not in FIPS mode while jess is | Startup probe reads `vault status` and `jess_fips_vault_aligned` gauge | Soft-warn: audit event `fips_mode_vault_misaligned`; do NOT hard-fail (Vault FIPS migration may legitimately lag a window) |
| macOS jessctl fips build — Go FIPS module on darwin routes through pure-Go for some primitives | `fipsmode.MustEnable()` returns OK on darwin but auditors may reject the build | Document: jessctl-darwin-fips is for **operator local convenience only**; production access via web SPA from a FIPS-validated workstation OS |
| AWS-LC-FIPS arm64 not yet certified, blocking arm64 jess-ironrdp-broker FIPS image | CI build script detects target arch; skips fips image build on arm64 with explicit log | Document arm64 broker is amd64-only in FIPS mode; track upstream AWS-LC arm64 cert ETA |
| `GODEBUG=fips140=on` not propagated to worker pods | Worker startup audit event missing fips marker | Helm chart sets env var in both controller and worker StatefulSets; admission policy verifies env presence on `jess-*` Deployments |

## Out of scope

- **Operating system kernel FIPS mode** — separate prereq managed by the host OS team. Documented as a deployment requirement, not a jess code change.
- **Customer-managed HSMs** — Vault PKCS#11 backend integration with on-prem HSM (Thales / Entrust / AWS CloudHSM) is a separate ADR; this one stays scoped to validated software modules.
- **Post-quantum cryptography migration** — ADR 0034 §Decisions #10 deferred until Go stdlib ships hybrid TLS 1.3 `X25519MLKEM768`. Cross-reference and revisit when Go 1.27+ ships PQ.
- **FIPS 140-3 Level 2/3/4 (tamper-evident hardware module)** — out of scope; jess targets Level 1 (validated software module on commodity hardware) which is the FedRAMP moderate baseline.
- **mearax / example / Falcon-ID FIPS posture** — parallel tracks in their respective repos.
- **OS-level FIPS workstation requirement for operators using jessctl** — documented as deployment guidance, not a jess code change.

2. **Vault Enterprise Plus license cost.** Self-hosted FIPS Inside requires the Plus tier. What is the annual cost? Is the budget approved? **Action:** confirm with HashiCorp account team before scheduling 5j-2e.
3. **HCP Vault Plus alternative.** $1.58/hr per cluster ≈ $13,832/yr per region. Multiply by N regions. Compare to self-hosted Enterprise Plus license. **Action:** TCO comparison before committing to deployment model.
4. **AWS-LC-FIPS arm64 ETA.** AWS-LC FIPS currently certifies amd64 only. arm64 cert is pending per AWS roadmap. **Action:** watch AWS blog; defer arm64 jess-ironrdp-broker FIPS image until upstream certs land.
5. **FedRAMP boundary definition.** Is Vault inside the jess FedRAMP boundary (so Vault FIPS Inside is mandatory) or outside (Vault is a "trusted external service" and only jess's interactions with it need to be FIPS)? **Action:** FedRAMP advisor consult — likely inside-boundary if jess uses Vault for cert minting at session-open, which materially affects every grant.
6. **MinIO FIPS.** OSS MinIO has no FIPS build; MinIO Enterprise does. If the recording's at-rest encryption needs FIPS validation (not just the signature), does that drive a MinIO Enterprise migration? **Action:** flag in FedRAMP SSP; the per-session Ed25519 signature provides integrity-tier evidence even with non-FIPS at-rest, but a strict auditor may push back.
7. **Falcon-ID FIPS sequencing.** Should Falcon-ID FIPS migration block jess FIPS GA, or can jess FIPS ship while Falcon-ID is still default-build with a documented SSP entry? **Action:** decide with security team; recommend parallel tracks, jess can GA independently with the caveat noted.
8. **Talon coupling.** Talon (IAP) at the edge. Same question as Falcon-ID. Same recommended answer.
9. **Operator workstation OS FIPS.** Does jessctl-darwin-fips count as FIPS-validated when macOS itself is not in FIPS mode? Likely no for auditors. **Action:** policy doc that for federal-tier access, operators MUST use a FIPS-validated OS (RHEL FIPS / Windows FIPS / macOS with system-wide FIPS — which has its own quirks).
10. **Go 1.26 native FIPS module v1.26.0.** Currently in "Modules In Process" list. Once cert issues, plan the upgrade. **Action:** track CMVP timeline; budget one 5j-2 follow-up minor for the version bump.
